# 05 · 变更说明（2026-11-16）

本次变更基于已推送到 `origin/main` 的提交 `1bb1006`，只处理设计评审中的三项 P0 风险。P1 / P2 项列在文末，本次未改动。

## 1. 扫码匹配不再误判错箱

**问题**：旧 `matchBarcode` 同时做双向 `LIKE '%'` 匹配，再用 `LIMIT 2` +「多候选中唯一在库即取」裁决。短码会命中库内箱码后缀并被静默采用：实测扫 `"1"` 返回 `W00305P10858011`（在库）与 `W00305P1085801`（已发出）两条，旧逻辑直接把在库那条登记出库。

**修改**：

| 文件 | 改动 |
| --- | --- |
| `app/.../barcode/BarcodeRules.kt` | 新增 `MIN_SCAN_NORM_LENGTH = 6`，`looksLikeBarcode` 统一使用该阈值，避免阈值两处不一致 |
| `app/.../data/dao/Daos.kt` | `matchBarcode` 拆为 `findExactByNorm`（精确）与 `matchBarcodeTail`（仅「扫码串以库内箱码结尾」），删除危险的反向 `LIKE` |
| `app/.../data/PackingRepository.kt` | 新增纯逻辑 `ScanResolver`：精确唯一 → 前缀唯一 → 单号+箱号唯一；任一层多条一律返回 `Ambiguous`，不再按在库状态猜测 |
| `app/src/test/.../BarcodeResolverTest.kt` | 新增 6 个回归用例，覆盖短码拒绝、多候选歧义、精确优先、回退与空结果 |

**行为变化**：带/不带分隔符、带前缀拼接串、只扫 `P108580-1` 仍可用；`1`、`801` 等短码不再识别；多义箱码弹出候选让用户核对，不再自动选在库箱。

## 2. 服务端成为箱状态唯一权威

**问题**：`GET /api/v1/packing` 只下发 payload + rev，PDA 新建箱默认 `IN_STOCK`；换机拉全量或多台 PDA 作业时，已发出箱会「复活」，可被重复出库。服务端上传也不校验箱是否已发出。

**修改**：

| 端 | 文件 | 改动 |
| --- | --- | --- |
| PC | `pc-server/server.py` | `packing` 每个箱附带 `status`（取自 `boxes.status`） |
| PC | `pc-server/server.py` | `receive_shipment` 改为幂等 + CAS：先查 `uid`，再按 `barcode_norm` 定位箱，用 `status='IN_STOCK'` 条件更新；任一箱已发出/不存在则返回 `409` + `conflicts`，整单不入库、不改状态 |
| Android | `importer/BoxPayload.kt` | 新增 `status` 字段，默认 `IN_STOCK`（兼容旧服务端） |
| Android | `sync/SyncClient.kt` | 解析 `status`；409 响应解析 `conflicts` 并给出中文提示 |
| Android | `data/dao/Daos.kt` | 新增 `hasLocalOutbound(boxId)`，判断该箱是否仍有未同步出库事件 |
| Android | `data/PackingRepository.kt` | `applyBoxes` 新建箱采纳服务端状态；更新箱时若有未同步出库事件则保留本地状态，否则采纳服务端；`scanOutbound` 拦截所有非 `IN_STOCK` 状态（含 `VOID`） |
| 文档 | `docs/02`、`docs/03` | 更新匹配规则、状态口径、409 错误码与冲突处理约定 |

**行为变化**：第二台 PDA 上传已被发出的箱会收到 409 和具体箱码，不再静默重复出库；离线扫码出库不会被后续拉取覆盖；换机后已发出箱仍显示为已发出。

## 3. 上传标箱不再全表扫描

**问题**：旧 `receive_shipment` 对每个上传箱遍历全表 2 万行并逐行 `json.loads`，100 箱的发货单约 200 万次解析，且全程持有全局锁，会阻塞所有请求。

**修改**：

- `boxes` 表新增 `barcode_norm` 列与索引；
- `init_db()` 对已有数据库自动加列并回填归一化条码，无需手工迁移；
- `import_xlsx()` 导入时写入归一化条码；
- 上传改为一次 `WHERE barcode_norm IN (...)` 查询 + 按 `source_key` 批量条件更新。

复杂度由 O(箱数 × 2 万) 降为 O(箱数)。现有 `pc-server/data/sync.db` 会在下次启动时自动升级。

## 阶段 2 · 解析契约固化 + 源表删行墓碑（2026-11-16 深夜）

### 1. 固化双端解析契约

**问题**：服务端 `parse_xlsx` 与 PDA `PackingImporter` 是两套独立解析实现，评审担心箱码/数量漂移。核对后当前样本两端 MERGE 结果完全一致（20929 箱 / 22554 明细 / 1639 重复 / 数量总和 608554 / source_key 边界与首箱字段吻合）——真正的风险不在算法，而在**契约文档错误**：`docs/02` 写"重复策略对拉取生效"，但同步数据一律是服务端 MERGE 结果，`LATEST`/`KEEP_ALL` 只影响本机手动导入。

**做法**：

| 文件 | 改动 |
| --- | --- |
| `app/src/test/.../CrossEndParseGoldenTest.kt` | 新增 golden 测试，把两端 MERGE 一致性固化为断言（箱数/明细/数量总和/source_key 边界/首箱字段） |

**效果**：任一端改动解析逻辑，golden 测试与脚本输出会立即不一致，把"隐性漂移"变成"显性回归"。

### 2. 源表删行落墓碑

**问题**：`import_xlsx` 只做 upsert，Excel 里删掉的箱会永久留在两端、库存虚增。阶段 1 的对账接口虽能发现 `extra`，但服务端自身没有墓碑语义。

**做法**：

| 端 | 文件 | 改动 |
| --- | --- | --- |
| PC | `pc-server/server.py` | 新增纯逻辑 `plan_import()`：对比本次解析与库中现状，算出写入计划与墓碑计划；`import_xlsx()` 接入它，删行的 `IN_STOCK` 箱标记 `VOID` 并递增 `rev`，使墓碑能经 `packing`/`reconcile` 下发；VOID 箱在源表重新出现时复活 |
| 测试 | `pc-server/test_tombstone.py` | 6 个纯逻辑单测（首次导入/删行/SHIPPED 不改/内容未变跳过/VOID 复活/内容变化） |
| 测试 | `pc-server/e2e_tombstone.py` | 14 项隔离端到端验证（临时库 + 合成 Excel，不碰真实 DB/台账） |

**安全边界**：首次导入不做墓碑；`SHIPPED` 箱不因源表删行改写（保留出库历史）；删行是软删除（保留记录），可恢复。

**语义演进**：有服务端墓碑后，删行箱以 `VOID` 保留在服务端，经 `stale`/`missing` 下发；`extra` 现在只表示"服务端从未有过的本地脏数据"。

## 阶段 3 · P1 收尾：盘点快照 + 两个小修复（2026-11-17）

### 1. 盘点改为快照（历史报表不再漂移）

**问题**：`stock_check_scan` 只存 `boxId`，报表与上传的实盘数都 `JOIN packing_item` 实时计算；而 `applyBoxes` 会 `deleteItems` 重建明细。源表一改，已结束批次的历史盘点报表和上报明细都会变——与出库用 `shipment_item` 快照的做法不一致。

**做法**：

| 端 | 文件 | 改动 |
| --- | --- | --- |
| Android | `data/entity/Entities.kt` | 新增 `StockCheckItem` 实体（scanId/checkId/boxId + 配件字段） |
| Android | `data/AppDatabase.kt` | 库版本 1→2，新增 `MIGRATION_1_2`：建表 + 索引 + 从当前 `packing_item` 回填历史扫描（best-effort） |
| Android | `data/dao/Daos.kt` | 报表查询（实盘数量、扫码明细、按配件汇总、异常汇总）全部从 `JOIN packing_item` 改为 `JOIN stock_check_item ON i.scanId=s.id`；新增快照插入/查询/按批次清理 |
| Android | `data/PackingRepository.kt` | `scanStocktake` 扫到箱时把 `lookup.items` 复制成快照；`cancelCheck` 同步清理快照 |
| Android | `sync/SyncClient.kt`、`SyncRepository.kt` | 盘点上传改读扫描快照（`itemsOfScan(scanId)`），不再读当前明细 |

**口径**：账面数（当前在库）仍是实时口径；实盘数（扫到的箱）是扫描时快照。两者按配件编码对比出差异。

### 2. 纯拼接箱码拆分不再切错边界

**问题**：`BarcodeRules.split` 用 `([Pp]\d{6,10})(\d{1,5})$` 猜单号/箱号边界，`W00305P10858012` 会被切成 `P1085801`+箱 `2`（真值应为 `P108580`+箱 `12`）。

**做法**：新增 `splitCandidates()` 穷举所有合理拆分（箱号 1~5 位），`lookup` 逐一查 `matchOrderBox` 并合并命中，交给 `ScanResolver` 裁决——唯一才采用、多条报歧义。保留原 `split()` 作为兼容入口。新增 3 个回归用例。

### 3. parse_xlsx 的 ZipFile 用 with 管理

`server.py` 把 `parse_xlsx` 拆成包装函数，`with zipfile.ZipFile(...)` 确保正常/异常路径都释放句柄，避免 Windows 上用户开着 Excel 时后续文件替换失败。解析结果不变（golden 基准复核一致）。

## 阶段 4 · PDA 数据库备份与恢复（2026-11-17）

背景：`allowBackup=false` 且此前无库导出，未上传的发货 / 盘点单据只存在 PDA 本机，设备丢失即丢单据。本阶段补上 App 内备份/恢复闭环。

### 1. 备份导出

- 新增 `backup/BackupArchive.kt`（纯逻辑，可 JVM 单测）：定义 zip 结构（`manifest.json` + `database/peijian.db` + `config/peijian.xml`），实现打包、读取 manifest、SHA-256 校验、解包。
- 新增 `backup/DbBackup.kt`（Android 层）：`wal_checkpoint(TRUNCATE)` 后再复制主库，连同 `SharedPreferences`（含 `lastRev`）一起打包；busy≠0 直接失败，不产出一个不一致的备份。备份写到 `/sdcard/Peijian/备份/`，不可写时退到 App 专属目录，并复用 FileProvider 分享（MIME `application/zip`，`Exporter.shareAs`）。
- manifest 记录 DB 版本 / 箱数 / 未上传单数 / 校验和 / 创建时间，供恢复前展示与校验。

### 2. 恢复导入

- 选 zip → 复制到缓存 → 校验格式/版本/SHA-256 → 确认弹窗（展示箱数、版本、未上传数、时间）→ 确认后**先自动备份当前库**，再关闭 Room（`AppDatabase.reset()`）、覆盖 `peijian.db` 与 `peijian.xml`、清除残留 `-wal`/`-shm` → 投递 restart 事件，由 `AppRoot` 重启进程（Room / ViewModel 持有旧连接，必须整进程重建）。
- 高版本备份拒绝在低版本应用恢复；校验和不符 / 非本应用备份 / 缺少条目均拒绝。
- `AppDatabase.VERSION` 常量供 manifest 记录与版本校验。

### 3. UI 与文档

- `SyncScreen` 新增「数据库备份与恢复」卡片（立即备份 / 从备份恢复 + 确认弹窗）；`AppViewModel` 新增 `backupDatabase/prepareRestore/confirmRestore/cancelRestore`；`UiEvent` 加 `restart` 标志。
- `docs/04` 第 6 节改为 App 内备份操作说明；`docs/02` 第 5 节补充 lastRev 随库备份的口径。

## 阶段 5 · 全量拉取分页（2026-11-17 下午）

背景：`packing?since=0` 一次性把 2 万箱读进内存（服务端 fetchall + 逐条 json.loads、PDA 整个响应读成 String 再解析成对象树），对账上线后 PDA 需同步全量摘要，问题更突出。

### 1. 服务端 keyset 游标分页

- 新增纯逻辑 `packing_page(conn, since, limit, after_key)`：以 `(rev, source_key)` 复合游标分页（展开成 `rev>? OR (rev=? AND source_key>?)`，避免 OFFSET 深翻页退化），返回 `has_more/next_since/next_after_key`。
- `limit<=0` 走全量分支，保持老客户端兼容；`limit` 上限 `PACKING_PAGE_MAX=2000` 防止超大请求。

## 阶段 6 · 服务端安全收尾：HTML 转义 + 连接关闭（2026-11-17 晚）

剩余 P2 中两项纯服务端、可脱离设备验证的问题，本阶段一并处理。

### 1. `/labels` 与首页的实时渲染改为转义输出

**问题**：`labels_page` 把箱码、客户编码、生产单号、配件编码/名称直接拼进 HTML；这些值来自 Excel 源表，若某格含 `<script>`/`onerror=` 之类内容，打印标签或打开首页时即被浏览器当脚本执行（存储型 XSS）。二维码分支还把 `code` 原样塞进 `img src`，未做 URL 编码。`index` 的「源表路径」和「导入结果 JSON」同样来自源表元数据。

**做法**：

| 文件 | 改动 |
| --- | --- |
| `pc-server/server.py` | 新增纯逻辑 `esc()`（`html.escape`）与 `label_img_src()`（先 `quote` 再 `esc`）；`/labels` 的 code/客户/单号/箱号/配件字段、下拉选项全部过 `esc`；二维码 `img src` 走 `label_img_src`；首页「源表路径」「导入结果」过 `esc`，配对二维码 URL 的 `text` 参数做 `quote`。局部变量 `html` 改名 `page`，避免与模块名冲突。 |

`from_no/to_no` 由 FastAPI 声明为 `int`，`kind/order` 仅用于等值比较，不涉及注入，保持原样。

### 2. SQLite 连接用后不关闭

**问题**：`with db() as conn:` 里 `sqlite3.Connection` 作为上下文管理器只负责提交/回滚，不会 `close()`；FastAPI 每个请求在线程池新建连接却不关闭，句柄一直累积到 GC，长时间运行有耗尽文件描述符的风险。

**做法**：把 `db()` 改为 `@contextmanager`，内部 `with conn:` 保留原有事务语义（正常提交、异常回滚），`finally: conn.close()` 保证连接一定释放。全部 12 处 `with db() as conn:` 调用点无需改动。

## 阶段 7 · 打包日期单一规则（2026-11-17 晚）

**问题**：`packDate` 是 Excel 里的「日历日」，但两端都按**本地时区**换算成毫秒——服务端用 naive `datetime.timestamp()`（取宿主时区），PDA 用 `ZoneId.systemDefault()`。golden 值 `1719936000000`（2024-07-03 00:00）成立的前提是本机恰好在 UTC+8：服务端部署到 UTC 的机器、或设备处于其他时区，同一序列号会漂移到相邻一天，导出/显示日期随之错位。这是阶段 5 之前就标注的 P1 残留。

**做法**：把打包日期锚定到固定 UTC+8，设备事件时间仍按本地时区（两者口径不同，勿混用）。

| 端 | 文件 | 改动 |
| --- | --- | --- |
| PC | `server.py` | 新增模块级 `PACK_DATE_TZ = timezone(timedelta(hours=8))`；`excel_date_to_millis` 用 tz-aware 午夜计算；新增 `millis_to_pack_date` 用于导出渲染；库存清单的打包日期列改用它。 |
| PDA | `logic/PackDate.kt`（新增） | 单一权威：`ZONE = ZoneId.of("UTC+08:00")`、`fromSerial`、`atDay`。 |
| PDA | `XlsxReader.kt` | `excelDateToMillis` 委托给 `PackDate.fromSerial`。 |
| PDA | `PackingImporter.kt` | `parseDate` 文本分支与 `formatDate` 改用 `PackDate`；移除本地时区依赖。 |
| PDA | `logic/DateText.kt` | **不变**，仍是 `systemDefault`，负责 `createdAt/scannedAt/shippedAt` 等真实时刻。 |
| 文档 | `docs/02` | 新增 3.5「打包日期单一规则」，说明基准/锚点/作用域与基准值。 |

**兼容性**：golden 基准 `1719936000000` 不变（本机 UTC+8 与新规则结果一致）；历史数据无需迁移，同一批次的毫秒值不变。

## 阶段 8 · 检查项目后的三处健壮性修复（2026-11-17 晚）

全量回归（Android 29 项单测 + 服务端 29 项单测 + golden 基准）通过后，复查出三处只在边界数据上触发的缺陷，本阶段一并修复，均不改变正常路径行为。

### 1. 同一箱码命中多箱时不再批量标发出

**问题**：`receive_shipment` 对每个码把**所有** `status='IN_STOCK'` 的命中箱都加进 `targets`。源表存在 1639 行重复箱号（MERGE 后仍有同码多箱），此时上传一张只扫了其中一箱的发货单，会把同码的另一箱也标成 `SHIPPED`，造成账面多出库且无法回退。

**做法**：抽出纯逻辑 `plan_shipment_targets(codes, found)`：只有「恰好命中一箱且为 IN_STOCK」才接受，缺失 / 已发出 /VOID / 同码多箱一律进 `conflicts`，整单 409。`receive_shipment` 改为调用它，逻辑不变处仅此。

### 2. `/labels` 箱号非数字不再 500

**问题**：`int(str(boxNo).split("-")[0])` 遇到文本箱号（`A1`、`箱-1`、空串等）抛 `ValueError`，整个标签页 500。

**做法**：新增纯逻辑 `box_seq(value)`：取首段，全数字才转 int，否则返回 0；`/labels` 的区间筛选改用它。

### 3. 上传遇到 409 不再堵住后续记录

**问题**：`SyncRepository.pushAll` 逐张上传，任一张收到 409 就抛异常中断，后面已完成的单据虽已标记同步，但剩余单据/盘点这批都不会再上传，且用户只看到一条冲突信息。

**做法**：`SyncClient` 新增 `ConflictException`（继承 `SyncException`，仅 409 抛出）；`pushAll` 逐单捕获冲突并跳过，`PushReport` 增加 `conflicts` 列表；UI 汇总提示「已上传 N 张；M 条冲突未上传（仍保留在本机）」。网络/令牌等其他错误仍整体抛出。
