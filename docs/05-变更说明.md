# 05 · 变更说明（2026-11-16）

本次变更基于已推送到 `origin/main` 的提交 `1bb1006`，只处理设计评审中的三项 P0 风险。P1 / P2 项列在文末，本次未改动。

## 1. 扫码匹配不再误判错箱

**问题**：旧 `matchBarcode` 同时做双向 `LIKE '%'` 匹配，再用 `LIMIT 2` +「多候选中唯一在库即取」裁决。短码会命中库内箱码后缀并被静默采用：实测扫 `"1"` 返回 `W00305P10858011`（在库）与 `W00305P1085801`（已发出）两条，旧逻辑直接把在库那条登记出库。

**修改**：

| 文件 | 改动 |
| --- | --- |
| `app/.../barcode/BarcodeRules.kt` | 新增 `MIN_SCAN_NORM_LENGTH = 6`，`looksLikeBarcode` 统一使用该阈值，避免阈值两处不一致 |
| `app/.../data/dao/Daos.kt` | `matchBarcode` 拆为 `findExactByNorm`（精确）与 `matchBarcodeTail`（仅「扫码串以库内箱码结尾」），删除危险的反向 `LIKE` |
| `app/.../data/PackingRepository.kt` | 新增纯逻辑 `ScanResolver`：精确唯一 → 前缀唯一 → 单号+箱号唯一；任一层多条一律返回 `Ambiguous`，不再按在库状态猜测 |
| `app/src/test/.../BarcodeResolverTest.kt` | 新增 6 个回归用例，覆盖短码拒绝、多候选歧义、精确优先、回退与空结果 |

**行为变化**：带/不带分隔符、带前缀拼接串、只扫 `P108580-1` 仍可用；`1`、`801` 等短码不再识别；多义箱码弹出候选让用户核对，不再自动选在库箱。

## 2. 服务端成为箱状态唯一权威

**问题**：`GET /api/v1/packing` 只下发 payload + rev，PDA 新建箱默认 `IN_STOCK`；换机拉全量或多台 PDA 作业时，已发出箱会「复活」，可被重复出库。服务端上传也不校验箱是否已发出。

**修改**：

| 端 | 文件 | 改动 |
| --- | --- | --- |
| PC | `pc-server/server.py` | `packing` 每个箱附带 `status`（取自 `boxes.status`） |
| PC | `pc-server/server.py` | `receive_shipment` 改为幂等 + CAS：先查 `uid`，再按 `barcode_norm` 定位箱，用 `status='IN_STOCK'` 条件更新；任一箱已发出/不存在则返回 `409` + `conflicts`，整单不入库、不改状态 |
| Android | `importer/BoxPayload.kt` | 新增 `status` 字段，默认 `IN_STOCK`（兼容旧服务端） |
| Android | `sync/SyncClient.kt` | 解析 `status`；409 响应解析 `conflicts` 并给出中文提示 |
| Android | `data/dao/Daos.kt` | 新增 `hasLocalOutbound(boxId)`，判断该箱是否仍有未同步出库事件 |
| Android | `data/PackingRepository.kt` | `applyBoxes` 新建箱采纳服务端状态；更新箱时若有未同步出库事件则保留本地状态，否则采纳服务端；`scanOutbound` 拦截所有非 `IN_STOCK` 状态（含 `VOID`） |
| 文档 | `docs/02`、`docs/03` | 更新匹配规则、状态口径、409 错误码与冲突处理约定 |

**行为变化**：第二台 PDA 上传已被发出的箱会收到 409 和具体箱码，不再静默重复出库；离线扫码出库不会被后续拉取覆盖；换机后已发出箱仍显示为已发出。

## 3. 上传标箱不再全表扫描

**问题**：旧 `receive_shipment` 对每个上传箱遍历全表 2 万行并逐行 `json.loads`，100 箱的发货单约 200 万次解析，且全程持有全局锁，会阻塞所有请求。

**修改**：

- `boxes` 表新增 `barcode_norm` 列与索引；
- `init_db()` 对已有数据库自动加列并回填归一化条码，无需手工迁移；
- `import_xlsx()` 导入时写入归一化条码；
- 上传改为一次 `WHERE barcode_norm IN (...)` 查询 + 按 `source_key` 批量条件更新。

复杂度由 O(箱数 × 2 万) 降为 O(箱数)。现有 `pc-server/data/sync.db` 会在下次启动时自动升级。

### 新增：POST /api/v1/reconcile 对账接口

**问题**：P0 建立了服务端状态权威，但缺少主动发现两端分歧的手段。换机、多 PDA、离线太久之后，若两端数据已经不一致，只能靠用户上报才发现问题。

**做法**：

| 端 | 文件 | 改动 |
| --- | --- | --- |
| PC | `pc-server/server.py` | 新增纯逻辑 `reconcile_diff(server_boxes, reported)` 计算 missing/extra/stale；新增 `POST /api/v1/reconcile`，只投影三列算差异、仅差异箱回查完整 payload，只读不改状态 |
| Android | `data/dao/Daos.kt` | 新增 `BoxDigest` 投影 + `allDigests()`（三列摘要）；新增 `markVoidByNorm()`（软删除） |
| Android | `sync/SyncClient.kt` | 新增 `DigestInput` / `ReconcileResult` 与 `reconcile()` 请求解析 |
| Android | `sync/SyncRepository.kt` | 新增 `reconcile()` 编排：missing/stale 用服务端数据 force 刷新；extra 置 VOID，但有未同步出库事件的箱跳过；完成后推进 `lastRev` |
| 测试 | `pc-server/test_reconcile.py` | 8 个纯逻辑单测 |
| 测试 | `pc-server/e2e_check.py` | 12 项真实 HTTP 端到端检查 |
| 文档 | `docs/03` | 新增对账接口章节（第 6 节），后续章节顺序顺延 |

**行为变化**：PDA 可在同步页触发对账，主动发现缺箱、陈旧箱、源表删行三类分歧并自动收敛；`extra` 的作废是软删除、可追溯，且不会丢弃有未同步出库事件的箱。
