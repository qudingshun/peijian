# 02 · 条码与数据规则

## 1. 箱码内容

**箱码 = 客户编码 + 生产单号 + 箱号**

默认用 `-` 连接：

```
W00305-P108580-1
```

- 分隔符可在 PDA「设置 → 箱码格式」里改（`-` `/` `_` 或无分隔），电脑端标签页固定用 `-`；
- 无分隔写法 `W00305P1085801` 也能扫到（见下方匹配规则）；
- 箱号建议用整数，`1`、`2`、`10`（不要 `1.0`、`001`）。

## 2. 归一化与匹配

所有比较先做 **归一化**：只保留字母数字并转大写。

```
W00305-P108580-1   →  W00305P1085801
w00305/p108580/01  →  W00305P10858001   （注意 01 ≠ 1，箱号请勿补零）
```

匹配顺序（`PackingRepository.lookup`）：

1. 归一化后不足 6 位直接拒绝：短码（如 `1`、`801`）可能是任意箱码的后缀，不能作为匹配依据；
2. `barcodeNorm` 完全相等；
3. 扫码串以库内箱码结尾（扫了带前缀的拼接串）；
4. 按 `生产单号 + 箱号` 反查（支持只扫 `P108580-1`，生产单号需含字母且不少于 4 位）。

任一层命中多条时一律提示 **箱码重复** 并列出候选，**不再按「唯一在库」自动消歧**——那会把误命中变成静默错箱出库。

## 3. Excel 数据规则

### 3.1 列映射（打包记录，17 列）

| # | 列名 | 落库字段 | 说明 |
| --- | --- | --- | --- |
| 1 | 打包日期 | `packDate` | Excel 日期序列号或 `yyyy-MM-dd` 等文本，统一存毫秒（当天 0 点） |
| 2 | 客户编码 | `customerCode` | 参与箱码 |
| 3 | 客户名称 | `customerName` | |
| 4 | 业务员 | `salesperson` | |
| 5 | 出口国 | `country` | |
| 6 | 生产单号 | `orderNo` | 参与箱码 |
| 7 | 箱号 | `boxNo` | 参与箱码，数值型去掉 `.0` |
| 8 | 长*宽*高(cm) | `dimension` | 文本原样 |
| 9 | 体积(㎥) | `volume` | 可空 |
| 10 | 毛重(kg) | `grossWeight` | 可空 |
| 11 | 配件编码 | `partCode` | 账务主键 |
| 12 | 英文描述 | `englishName` | |
| 13 | 配件名称 | `partName` | |
| 14 | 数量 | `quantity` | 四舍五入为整数 |
| 15 | 整机型号 | `machineModel` | 参与"同箱同配件"判定 |
| 16 | 打包单位 | `packingUnit` | 箱级字段 |
| 17 | 备注 | `remark` | 箱级与明细各存一份，导出时合并去重 |

表头行为自动探测：前 30 行里同时包含「配件编码」「生产单号」的行即为表头。

### 3.2 合并单元格

源表把同一箱的客户/单号/箱号/尺寸等写在合并区域里。导入时按合并区域把左上角的值回填到整块，否则会出现"有配件没箱号"的孤儿行。

### 3.3 一箱多配件

一箱内多行配件（最多 17 行）→ 一个 `packing_box` + 多条 `packing_item`。

### 3.4 重复箱号处理策略

同「客户编码 + 生产单号 + 箱号」出现多行时（源表约 1060 行）：

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `MERGE`（默认） | 同箱同配件编码 + 同整机型号 → 数量相加；不同配件 → 追加明细 | 拆箱补齐、分多次打包同一箱 |
| `LATEST` | 取打包日期更晚的一行作为整箱内容；日期相同仍合并 | 箱号被重新使用 |
| `KEEP_ALL` | 重复箱自动加 `-2`/`-3` 后缀，箱码随之变化 | 确实有两个物理箱且必须分开管 |

**解析权威与策略作用域（重要）**：

- **服务端 `parse_xlsx` 是唯一解析权威，固定用 `MERGE`**。同步拉取（`/api/v1/packing`、`reconcile`）下发的箱码、数量、明细一律是服务端 MERGE 的结果，PDA 不做二次解析。
- PDA「设置 → 重复箱号处理」的 `LATEST` / `KEEP_ALL` **只影响本机手动导入 Excel**（离线首次灌数等场景），**对同步拉取无效**——否则本地会生成服务端不存在的箱码（如 `-2` 后缀），对账时报 `extra`、库存对不上。同步一旦发生，服务端数据覆盖本地策略结果。
- 因此**现场统一使用默认 `MERGE`**；非 MERGE 策略仅在没有服务端、纯本地应急时使用，且这部分数据不会回传箱主数据。

**双端一致性回归**：`app/src/test/.../CrossEndParseGoldenTest.kt` 与 `pc-server/golden_check.py`锁定同一份 Excel 的 MERGE 解析基准（箱数 / 明细 / 数量总和 / source_key 边界 / 首箱字段）。改动任一端解析逻辑，两边输出必须同步更新，否则视为回归。当前样本基准：20929 箱 / 22554 明细 / 数量总和 608554。

### 3.5 异常数据

| 情况 | 处理 |
| --- | --- |
| 箱号为空 | 按 `0` 占位入箱（便于先入库）；建议源头补全 |
| 配件编码为空但有单号 | 跳过该行，计入 `skippedRows` |
| 数量为空/非数字 | 记 0 |
| 日期为空 | `packDate = null`，导出留空 |

## 4. 库存与账务口径

- **箱状态**：`IN_STOCK`（在库）/ `SHIPPED`（已发出）/ `VOID`（保留）。服务端为唯一权威，通过同步接口的 `status` 字段下发；PDA 仅在本机仍有未上传的出库事件时保留本地状态。
- **库存清单**：只包含 `IN_STOCK` 的箱，一行 = 一个箱内一种配件（与源表同构）。
- **物料汇总**：只统计 `IN_STOCK`，按 `partCode` 分组，`SUM(quantity)`、`COUNT(DISTINCT boxId)`、`COUNT(*)`。
- **出库**：发货完成时把箱内配件写入 `shipment_item` 作为**快照**，此后即使源表改数量，历史出库不变。
- **盘点差异**：按配件编码比较「当前在库合计」与「本批次扫到的在库箱合计」。
- 同一配件编码的 `partName` / `englishName` / `machineModel` 取首个非空值展示，数量严格按编码合计。

## 5. 同步版本号（rev）

- 电脑端每次导入内容有变化时 `rev + 1`，变化过的箱都写入新 `rev`；
- PDA 记录本地已拉到的最大 `rev`，下次只请求 `rev > 本地` 的箱；
- 落库成功才推进本地 `rev`，避免网络中断导致漏数据；
- 同一箱 `rev` 更旧时默认不覆盖（`force=false`），手动导入 Excel 时可强制覆盖。
